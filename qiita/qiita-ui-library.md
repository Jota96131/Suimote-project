# 【個人開発】ReactのUIライブラリ、なんとなく選んでない？5つのカテゴリで整理してみた

## はじめに

個人開発で水泳の練習記録アプリを作っています。
「UIライブラリどうしよう」と思ったとき、なんとなくMUIを入れたり、とりあえずTailwindを使ったりしがちですよね。

今回は **「なぜそのライブラリを選んだのか」を説明できるようになる** ことを目指して、ReactのUIライブラリを **5つのカテゴリ** に整理してみました。

## 結論：UIライブラリは5種類に分けられる

| カテゴリ | 一言で言うと | 代表例 |
|---------|------------|--------|
| ① ユーティリティCSS | クラス名を並べてスタイルを組む | Tailwind CSS, Bootstrap, UnoCSS |
| ② フル機能コンポーネント | 完成品のボタンやテーブルがもらえる | MUI, Ant Design, Mantine, Chakra UI |
| ③ ヘッドレスUI | 見た目なし・動きだけもらえる | shadcn/ui, Radix UI, Headless UI, React Aria |
| ④ CSS-in-JS | JSの中にCSSを書く | styled-components, Emotion, Vanilla Extract |
| ⑤ 素のCSS系 | 追加ライブラリなし | CSS Modules, Sass, Plain CSS |

**これだけ覚えておけば、どのライブラリが出てきても「あ、これは②のフル機能型だな」と分類できます。**

## たとえ話で理解する

### ① ユーティリティCSS → レゴブロック

小さなパーツ（`bg-blue-500`, `text-lg`, `p-4`）を組み合わせて自分で作る。

```tsx
<button className="bg-blue-500 text-white font-bold py-2 px-4 rounded">
  保存
</button>
```

**メリット：** 自由度が高い、軽量、ビルドサイズが小さい
**デメリット：** ボタンもテーブルも全部自分で組む必要がある

### ② フル機能コンポーネント → 完成品の家具セット

テーブル、ボタン、モーダルなど出来上がったものが届く。

```tsx
import { Button, Table } from '@mui/material';

<Button variant="contained">保存</Button>
```

**メリット：** すぐ使える、コンポーネント数が豊富
**デメリット：** バンドルサイズが大きい、デザインの自由度が低い

### ③ ヘッドレスUI → 骨組みだけの家具キット

「引き出しの開閉」や「アクセシビリティ」は作ってあるけど、見た目は自分で塗る。

```tsx
// shadcn/ui - コードがプロジェクトにコピーされる
import { Button } from "@/components/ui/button";

<Button variant="outline">保存</Button>
```

**メリット：** アクセシビリティ担保済み、完全にカスタマイズ可能
**デメリット：** Tailwindの知識が前提（shadcn/uiの場合）

### ④ CSS-in-JS → コンポーネントごとに服を着せる

JSファイルの中にスタイルを直接書く。

```tsx
const StyledButton = styled.button`
  background: blue;
  color: white;
  padding: 8px 16px;
`;
```

**メリット：** コンポーネント単位でスコープされる
**デメリット：** ランタイムコスト（実行時にCSSを生成するため）

### ⑤ 素のCSS → 布から服を縫う

```css
/* Button.module.css */
.button {
  background: blue;
  color: white;
}
```

**メリット：** 依存ゼロ、最もシンプル
**デメリット：** 全部手作業、大規模になると管理が辛い

## もう少し詳しく：各カテゴリの代表ライブラリ

### ① ユーティリティCSS

| ライブラリ | 特徴 |
|-----------|------|
| **Tailwind CSS** | 最も人気。ユーティリティクラスの代名詞 |
| **Bootstrap** | 老舗。情報量が圧倒的に多い |
| **UnoCSS** | Tailwind互換でビルドがより速い |
| **Bulma** | Flexboxベース。JSに依存しない |

### ② フル機能コンポーネント

| ライブラリ | 特徴 |
|-----------|------|
| **MUI** | Material Design。コンポーネント数最多 |
| **Ant Design** | Alibaba発。テーブル・フォームが非常に強い |
| **Chakra UI** | APIが直感的。アクセシビリティ重視 |
| **Mantine** | hooks充実。日付ピッカー等が標準搭載 |
| **NextUI** | モダンデザイン。Tailwindベース |
| **Fluent UI** | Microsoft製。Office風UI |
| **PrimeReact** | エンタープライズ向け。コンポーネント数が多い |

### ③ ヘッドレスUI

| ライブラリ | 特徴 |
|-----------|------|
| **shadcn/ui** | Radix UI + Tailwind。コードがコピーされるので自由にカスタマイズ可能 |
| **Radix UI** | shadcn/uiの基盤。アクセシビリティが完璧 |
| **Headless UI** | Tailwind公式。コンポーネント数は少なめ |
| **React Aria** | Adobe製。WAI-ARIA準拠が最も厳密 |
| **Ark UI** | Chakra UIチームの新作。フレームワーク非依存 |

### ④ CSS-in-JS

| ライブラリ | 特徴 |
|-----------|------|
| **styled-components** | 最も有名なCSS-in-JS |
| **Emotion** | MUIの内部でも使用。柔軟なAPI |
| **Vanilla Extract** | ゼロランタイム。ビルド時に静的CSS生成 |
| **Panda CSS** | Tailwind + CSS-in-JSの融合。型安全 |
| **Linaria** | ゼロランタイム。styled-components風の記法 |

### ⑤ 素のCSS系

| 手法 | 特徴 |
|------|------|
| **CSS Modules** | ファイル単位でスコープ。Vite標準対応 |
| **Sass/SCSS** | CSSの拡張。変数・ネスト・mixinが使える |
| **Plain CSS** | 依存ゼロ。小規模なら十分 |

## 実際に自分のプロジェクトで選んだ話

### プロジェクトの前提

- **アプリ：** 水泳の練習記録アプリ（Suimote）
- **技術スタック：** React + Vite + TypeScript
- **規模：** 小規模SPA
- **必要な画面：** 練習記録の一覧表示（テーブル）

### 各カテゴリの検討

| カテゴリ | 判断 | 理由 |
|---------|------|------|
| ① Tailwind単体 | ○ | 軽量でViteと相性抜群。ただしテーブルは自作 |
| ② MUI | △ | 小規模アプリには重すぎる。大砲でスズメを撃つ感じ |
| ③ shadcn/ui | ◎ | 軽量＋テーブルあり＋カスタマイズ自由 |
| ④ CSS-in-JS | △ | わざわざ入れる理由が薄い。ランタイムコストも気になる |
| ⑤ 素のCSS | ○ | 今のままでもいける。ただし画面が増えると管理が辛い |

### 選定：shadcn/ui

選んだ理由は3つです。

1. **軽量**：ヘッドレスUI（Radix UI）＋ Tailwind CSSの組み合わせで、バンドルサイズが小さい
2. **必要なコンポーネントが揃っている**：練習記録一覧に使えるTableコンポーネントがある
3. **カスタマイズが自由**：コードが自分のリポジトリにコピーされるので、ブラックボックスにならない

## 選定で大事なこと

ライブラリ選定で面接やチーム開発で問われるのは **「なぜそれを選んだか」** です。

ポイントは3つ：

1. **他の選択肢を知っていること** → 「MUIしか知りません」ではなく「5カテゴリの中から検討しました」
2. **プロジェクトの要件に合わせていること** → 「なんとなく」ではなく「小規模SPAだから軽量なものを選んだ」
3. **トレードオフを理解していること** → 「MUIは便利だけどバンドルサイズが大きい」のように、メリ・デメを説明できる

## まとめ

| 覚えること | 内容 |
|-----------|------|
| 5つのカテゴリ | ユーティリティCSS / フル機能型 / ヘッドレスUI / CSS-in-JS / 素のCSS |
| 選定基準 | プロジェクト規模、必要なコンポーネント、バンドルサイズ、カスタマイズ性 |
| 伝え方 | 「他の選択肢を知った上で、理由をもって選んだ」 |

**「なんとなく」ではなく「選んだ理由を説明できる」**。これだけで、個人開発でもチーム開発でも信頼度が上がります。
