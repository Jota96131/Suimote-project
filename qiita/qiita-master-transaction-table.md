# 【DB設計】マスターテーブルとトランザクションテーブルの違いを整理する

## はじめに

個人開発で水泳の練習記録アプリ「Suimote」を作っています。
DB設計を進める中で、**マスターテーブル**と**トランザクションテーブル**という考え方に触れました。

この2つはDB設計の基本ですが、最初は違いがピンときませんでした。
この記事では、自分のアプリを例にしながら整理します。

---

## ひとことで言うと

- **マスターテーブル** → 「選択肢」を置いておく棚
- **トランザクションテーブル** → 「日々の出来事」を記録するノート

---

## マスターテーブルとは

マスターテーブルは、**システムで使う基本データ（参照データ）** を格納するテーブルです。

特徴はこうです。

- めったに変更されない
- 他のテーブルから**参照される側**
- 「コード」と「名称」のようなシンプルな構造が多い

例えば、エリアのマスターテーブルはこんなイメージです。

```sql
CREATE TABLE areas (
  id SERIAL PRIMARY KEY,
  area_name TEXT NOT NULL
);
```

| id | area_name |
|----|-----------|
| 1  | 東京 |
| 2  | 大阪 |
| 3  | 名古屋 |
| 4  | 福岡 |

都道府県、泳法の種類、施設の一覧など、**あらかじめ決まっている選択肢**がマスターテーブルに入ります。

---

## トランザクションテーブルとは

トランザクションテーブルは、**日々発生するデータ（イベントデータ）** を格納するテーブルです。

特徴はこうです。

- ユーザーの操作に応じて**どんどん増えていく**
- マスターテーブルの値を**参照する側**
- 日付やユーザーIDなど、「いつ・誰が」の情報を持つことが多い

Suimoteでは `practice_records` がこれにあたります。

```sql
CREATE TABLE practice_records (
  id SERIAL PRIMARY KEY,
  date DATE NOT NULL,
  distance INTEGER,
  time INTEGER,
  stroke TEXT,
  facility TEXT,
  memo TEXT,
  user_id UUID REFERENCES auth.users(id),
  created_at TIMESTAMPTZ DEFAULT now()
);
```

ユーザーが練習を記録するたびに、1行ずつ増えていきます。

---

## 2つの違いを比較する

| | マスターテーブル | トランザクションテーブル |
|---|---|---|
| **役割** | 基本データ（参照用） | 日々発生するデータ |
| **更新頻度** | 低い（管理者がたまに更新） | 高い（ユーザーが日常的に追加） |
| **データ量** | 少ない（数十〜数百件） | 多い（数千〜数百万件） |
| **参照関係** | 参照**される**側 | 参照**する**側 |
| **例（一般）** | 都道府県、商品カテゴリ、部署 | 注文履歴、ログイン履歴、投稿 |
| **例（Suimote）** | エリア、泳法、施設 | 練習記録 |

---

## なぜ分けるのか

「エリア名を直接 `practice_records` に文字列で入れればいいのでは？」と最初は思いました。

```sql
-- エリアを文字列で直接持つパターン
INSERT INTO practice_records (user_id, date, distance, area)
VALUES ('xxx', '2026-03-16', 2000, '東京');
```

これでも動きますが、問題が出てきます。

### 1. 表記ゆれが起きる

```
'東京' '東京都' 'tokyo' 'Tokyo'
```

ユーザーが自由入力すると、同じ意味のデータがバラバラになります。集計するときに困ります。

### 2. 名称変更時にすべての行を更新する必要がある

もし「東京」を「東京エリア」に変えたくなったら、何万件もの練習記録を全部書き換えることになります。

### 3. マスターテーブルで解決できる

```sql
-- practice_recordsはIDだけ持つ
INSERT INTO practice_records (user_id, date, distance, area_id)
VALUES ('xxx', '2026-03-16', 2000, 1);

-- 名称はマスターから引く
SELECT p.date, p.distance, a.area_name
FROM practice_records p
JOIN areas a ON p.area_id = a.id;
```

IDで参照するので表記ゆれは起きません。名称を変えたいときもマスターの1行を更新するだけです。

## Suimoteでの使い分け

現在の実装と、今後の拡張予定を整理するとこうなります。

```
【マスターテーブル（参照データ）】
  areas       … エリア一覧（MVP4で実装予定）
  strokes     … 泳法一覧（将来検討）
  facilities  … 施設一覧（将来検討）

【トランザクションテーブル（イベントデータ）】
  practice_records … 練習記録（実装済み）
```

マスターテーブルを整備することで、将来こういったクエリが簡単に書けるようになります。

```sql
-- エリアごとの累計距離ランキング
SELECT
  a.area_name,
  SUM(p.distance) AS total_distance
FROM practice_records p
JOIN users u ON p.user_id = u.id
JOIN areas a ON u.area_id = a.id
GROUP BY a.area_name
ORDER BY total_distance DESC;
```

## まとめ

| ポイント | 内容 |
|----------|------|
| マスターテーブル | 「選択肢」を管理する。めったに変わらない基本データ |
| トランザクションテーブル | 「出来事」を記録する。日々増えていくデータ |
| 分ける理由 | 表記ゆれ防止、名称変更の容易さ、データの整合性を保つため |
| 参照の方向 | トランザクション → マスター（IDで参照する） |

最初は「全部1つのテーブルに入れればいいのでは」と思いがちですが、**マスターとトランザクションを分けることで、データがきれいに保たれ、将来の集計や機能追加が楽になります。**
